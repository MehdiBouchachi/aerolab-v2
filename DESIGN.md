# AeroLab interface direction

The dashboard serves site operators who need to spot controller attention and inspect readings quickly. Its color system uses one blue for brand, navigation, links, focus, and primary actions. Amber is reserved for attention or degraded status; red is reserved for critical incidents and errors. Routine and healthy states use neutral text, with blue only for interactive emphasis. Light and dark surfaces use neutral slate values. Text and icons carry meaning alongside color.

The canonical visual tokens live in `apps/web/src/styles/app.css` as CSS custom properties. This document records their intent; the stylesheet owns exact runtime values. `:root` defines light mode and `:root[data-theme=dark]` defines dark mode. The theme switch is shared by the authenticated shell and login, and the choice is stored locally in the browser. First visit follows the system setting.

Buttons share one 40px target, 8px radius, weight, focus ring, and disabled treatment. One solid blue button marks the primary decision in a task area; outlined neutral buttons support secondary actions. Disabling an account uses the subdued red danger variant. Text buttons are reserved for low-emphasis utility actions, while segmented and underlined view selectors retain their navigation treatment.

Layout uses a narrow navigation rail on desktop, a compact site status strip, one shared four-number summary surface, and two-column unit cards. Each card uses a single readings row and plain metadata rows; individual readings are not boxed. Shared outline icons in `apps/web/src/components/Icon.tsx` are used sparingly for navigation and connection state. The overview-specific refinement lives in `apps/web/src/styles/dashboard.css`, loaded after shared styles. Cards collapse to one column on phones. All simulator, freshness, and unverified-flow wording stays explicit.

On phones (700px and narrower) the app uses a native shell, defined in `apps/web/src/styles/mobile.css` (loaded last): a sticky top bar with the brand, a back button on unit pages, and an account icon; a bottom tab bar with the three destinations; and a one-line status strip. Account controls open as a bottom sheet over a dimmed backdrop; tapping the backdrop or pressing Escape closes it. The overview summary is a single four-cell row. Unit cards show the name, simulator tag and status on one line, the four readings in one row with short names (full names stay available to screen readers), and pump/programme facts on one line. Unit sections and alert filters are segmented controls; administration views are scrolling chips. Primary form actions span the width. Inputs use 16px text so iOS does not zoom. The site is installable (`manifest.json`, icons, safe-area insets) and opens without browser chrome from the home screen. Cards, detail panels, and forms use the page width without horizontal clipping.

Unit cards put the unit name and current status together at the top, readings in a compact row, pump and programme as supporting facts, and the detail link in the footer. Only the link is interactive; on desktop the card itself does not imply a click target. On phones the link's tap area covers the whole card, which is still a single link.

Unit detail follows the same order: name and plain-language status, connection/pump/safety/programme facts, then current sensor readings. Firmware and buffer details remain available in a disclosure so the main status stays readable. Missing and invalid readings keep explicit text.

History shows all five sensor trends as aligned rows with a shared time axis, allowing timing changes to be compared at once. Each row shows the reading at the selected time and the actual low/high values; each line has an independent, labeled scale because the sensors use different units. A compact legend explains gaps and invalid readings. Lines never draw across a missing-data gap. Scales keep a minimum visible span so small noise is not exaggerated.
One keyboard-accessible time scrubber selects the same recorded moment across all rows. The selected timestamp, values, and vertical markers update together; missing or invalid values stay explicit.
The selected time stays fixed while the pointer moves across the charts. Only the scrubber changes it, for mouse, keyboard, and touch input. A subtle midpoint guide and three shared time labels help align the sensor trends.

Programme editing is a bounded task panel with short context. Pump on/off values form the cycle timing group; maximum continuous on and reservoir protection form the safety group. Each field shows its allowed range and units, with inline errors after interaction. A separate review step comes before a request is sent. The panel never implies a request is already applied.
The fixed reservoir protection sits beside the maximum continuous on field, so the safety group has no unused half-width column. The current and proposed versions remain visible without repeating the unit name in the form.

Unit detail uses three URL-addressable sections: Overview, History, and Programme. The unit title and status remain above the section navigation. This keeps the first screen short and lets operators open history or timing controls directly.

Alerts use a quiet status panel when a filter has no records. Active and History are plain underlined tabs. When faults exist, each record shows severity and title first, then the linked unit, cause, suggested action, and timestamps. Acknowledgement is a separate action and never appears to resolve the fault. Amber and red are reserved for warning and critical severity.

Administration uses a short section index for direct access to storage, controllers, accounts, phone pairing, and activity. Storage health leads with an explicit state and supporting measurements. Device and account tables share a compact row rhythm; account actions remain labeled with the username. Pairing instructions and the one-time code stay in one section, and audit events use a simple chronological list.
Administration views are selected by `?view=storage`, `controllers`, `users`, `pairing`, or `activity`, with only one view shown at a time. Users is a dedicated management view with search, account creation on demand, role changes, and enable/disable actions. The current view is a link, so Back, refresh, and sharing preserve it.

Type uses the installed system sans stack, with tighter display spacing and quieter utility labels. No remote font or asset is required, preserving offline use.
